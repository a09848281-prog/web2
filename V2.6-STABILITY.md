# Remote Camera Web2 v2.6 Stability Preview

**Branch:** `preview/v2.6-stability`  
**Android package ID:** `jp.a09848281.remotecamera.v26`  
**Android version:** `2.6.0-preview` / versionCode `427`  
**PWA:** `https://a09848281-prog.github.io/web2/v2.6/`  
**Purpose:** prioritize the camera, microphone, stop, and standby lifecycle over adding features.

## What changed

### Screen sharing removed
The Android MediaProjection capture pipeline, second WebRTC video track, screen-share controls and screen remote-control AccessibilityService have been removed. The normal camera stream remains the only video stream.

### Browser microphone is push-to-talk only
The Web page and RTC connection no longer call `getUserMedia()` for the microphone. The audio sender is negotiated without acquiring a local device. On a PTT press, the browser requests an audio track and attaches it to the sender. On release, the sender is detached and the stream tracks are stopped. The same release path runs on disconnect and connection-loss cleanup. The three-minute safety timer remains.

Connection reservation no longer pre-requests microphone permission. This prevents a reservation or simply opening the page from activating the browser's microphone indicator.

### Stop and standby lifecycle
The notification's **待機を停止** action is handled by `StopMonitoringReceiver`, which marks monitoring disabled and calls `stopService()`. The Android app's Stop button uses the same helper. Service shutdown cancels polling, disposes the RTC engine, closes camera/audio resources, turns off an app-owned torch if present, releases stream and display wake locks, releases Wi-Fi lock, clears active preferences, and removes the notification. Polling jobs explicitly rethrow coroutine cancellation rather than converting stop into a startup error. The notification update helper also refuses to repost any notification after `monitoringEnabled` becomes false; this prevents a late error callback from recreating the old “initial connection failed” notice after stop.

Disconnect from Web first releases its own microphone, waits only a bounded period for Android's DataChannel acknowledgement, sends a GAS bye fallback, and closes the browser PeerConnection. A completely unreachable network can still prevent an acknowledgement; Android's ICE/session cleanup remains the fallback.

### Android display-awake
The Android app has a local **自動消灯防止** setting. The Web viewer has a separate **Android自動消灯防止** toggle which sends an RTC DataChannel command to the service. The service uses a screen-dim wake lock while the preference is on and releases it when switched off or when monitoring stops.

This feature may increase battery consumption. It prevents normal automatic display sleep while the OS honours the wake lock; it does not disable device security, remove a PIN/pattern/password, or guarantee that the device will unlock itself after the user manually locks it. The local Activity also uses `FLAG_KEEP_SCREEN_ON` while visible.

### Noise suppression limits
The slider is 0–100 with 0 meaning OFF. Any value from 1–100 requests the standard hardware NoiseSuppressor ON state. The Android `NoiseSuppressor` API and the current WebRTC Java audio module expose an enabled state, not a continuous strength parameter. Therefore the slider's number is a requested/UI value, not a true percentage of cancellation intensity. The hardware audio module is created with the RTC media engine, the standard hardware suppressor can be switched ON/OFF live during an active session. The slider is wired to this live switch; it does not provide proportional strength control. If the hardware audio effect cannot be changed during the session, the service reports that it will apply on the next audio start.

This is deliberately kept as a transparent binary control instead of pretending that values such as 20 and 90 produce different measured levels.

### Flashlight behavior
When the flashlight is already off, cleanup no longer calls the camera torch API to turn it off again. When it is on, the code remembers the exact camera ID that owns the torch and tries to release that same camera's torch state. Android may still reject turning a flash on if the camera driver reports a resource conflict with the active camera stream.

## Checks

The GitHub Actions workflow runs:

1. JavaScript syntax checks for the PWA and Service Worker.
2. GAS syntax check.
3. Node test suite, including PTT lifecycle and stop/standby regression tests.
4. Project consistency checks for HTML IDs, no screen-share pipeline, microphone lifecycle, remote display-awake state, stop notification and torch cleanup.
5. Android Gradle debug APK build.

The release branch is published separately under `/v2.6/`; the existing root site and `/v2.1/` and `/v2.5/` paths are assembled unchanged by the Pages workflow.

A successful GitHub Actions build is not a physical hardware test. The Galaxy A22 5G on Android 13, iPad Safari microphone permission behavior, brightness/wake-lock behavior and flashlight hardware still need real-device testing.

## Installation and rollback

The APK uses a separate Android application ID from the v2.5 app. It can be installed beside v2.5 and does not overwrite its private app data. Because Android private storage is package-scoped, v2.6 starts with its own settings and must be paired again using a new pairing code. Keep v2.5 installed until the new build has passed device tests.

## Kept unchanged

The old `main`, `preview/v2.1.2-stability`, `preview/v2.5-remote-screen` and the separate old `web` repository are not overwritten by this release branch.
