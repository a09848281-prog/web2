## Changes in v2.6.1

### Web microphone starts with the RTC connection

- The browser requests microphone access as the connection is being established.
- The request is non-blocking for camera/video setup. If permission is denied or unavailable, viewing can continue and the microphone can be enabled again from the Web microphone button.
- The button is an ON/OFF toggle rather than a press-and-hold PTT control.
- The microphone track is attached with `RTCRtpSender.replaceTrack()` and stopped/detached on OFF, disconnect, RTC failure, or when the viewer page is backgrounded.
- Incoming Android audio remains enabled while the Web microphone is transmitting, so the connection is full duplex.
- This behavior is subject to browser microphone permission and iPad Safari lifecycle restrictions. A browser may suspend a background tab.

### Adjustable Web-side noise gate

The old Android hardware NoiseSuppressor slider could only request ON/OFF and did not represent a true 0–100 intensity. v2.6.1 moves the adjustable control to the Web Audio receive path.

- `0`: bypasses the gate completely.
- `1–100`: progressively increases attenuation of low-level audio near the estimated background-noise floor.
- The processor is an adaptive noise gate, not AI denoising or full spectral noise cancellation. It can also attenuate quiet speech, especially at high values.
- The selected value is stored in the Web viewer's local storage and applied to the incoming Android microphone audio.
- The Worklet is preloaded by the service worker. A compatible fallback is used where AudioWorklet is unavailable.

### Android screen sleep prevention is Web-only

- The local sleep-prevention button and its explanatory UI were removed from the Android APK.
- The Web viewer is the only control surface for Android sleep prevention.
- The service attempts to acquire a screen wake lock and reports its actual held state in telemetry.
- Web waits for the Android DataChannel acknowledgement before changing the displayed ON/OFF state. A failed request no longer leaves the UI optimistically displaying ON.
- Disabling monitoring releases the wake lock and resets the saved state.

This setting can wake/keep the display on and increases battery use. Android's keyguard and device security lock are not disabled. OEM power-management settings may still affect behavior.

### Zoom can be panned

- The viewer supports dragging the zoomed video horizontally and vertically.
- Movement is bounded so the image cannot be dragged completely out of view.
- Reset returns zoom and pan to the centered 100% state.
- This is viewer-side zoom; it does not change the video resolution sent by Android.

### Flashlight behavior and Android camera-resource limitation

- Torch state follows `CameraManager.TorchCallback` and the service reports the actual torch state instead of relying only on the last requested value.
- If Android reports that the torch is unavailable, the Web status is updated to OFF.
- A failed ON request is cleared. The service no longer silently retains it and retries after a camera-facing switch; this prevents the light from unexpectedly turning on only after the user changes cameras.
- The current implementation still uses Android's public `CameraManager.setTorchMode()` API. Android documents that this call can fail when the camera device or other camera resources needed for the flash are in use. Therefore, **simultaneous rear-camera video capture and rear flashlight operation is not guaranteed**. On a phone that rejects this combination, this branch reports the failure rather than pretending it is ON.

Android API reference: https://developer.android.com/reference/android/hardware/camera2/CameraManager#setTorchMode(java.lang.String,boolean)

A true device-specific simultaneous torch implementation may require changing the WebRTC camera capture pipeline so that the active camera session itself applies `CaptureRequest.FLASH_MODE_TORCH`. The current public capturer interface does not expose that control directly, and using reflection against private WebRTC camera-session internals would add fragility and crash risk. That deeper capture-pipeline refactor is not claimed as completed in v2.6.1.

## Stability safeguards retained

- Android service shutdown continues to cancel polling, dispose RTC, release camera/audio and power resources, turn off the torch when owned, and remove the foreground notification.
- Android camera/control commands remain serialized through the DataChannel command mutex.
- Viewer disconnect still releases the local Web microphone before waiting for a bounded remote acknowledgement and sending the GAS bye fallback.
- Screen sharing, remote screen control, recordings, audio recording and image saving remain excluded.
- Existing v2.1, v2.5 and v2.6 preview paths remain separate in the GitHub Pages deployment.

## Device test checklist

- Connect from iPad and allow microphone permission. Confirm the Web microphone button changes to ON and Android receives the audio.
- Confirm Android sound continues to be heard while the Web microphone is ON (full duplex).
- Switch the Web microphone OFF and verify the browser microphone indicator turns off.
- Move noise suppression from 0 to 100 while hearing a steady background sound; confirm that higher values attenuate low-level sound and that quiet speech can be reduced.
- Toggle Android sleep prevention ON and OFF from Web. Confirm the phone screen stays awake when ON and the Web button reflects the Android acknowledgement.
- Zoom to 200% or 300%, drag to all four directions, and use Reset.
- Test the rear camera flashlight while the rear camera is active. Record the exact Android error if it is rejected; do not treat switching to the front camera as a successful simultaneous-rear-camera test.
- Disconnect and verify browser mic release, Android session cleanup, and torch OFF state.
